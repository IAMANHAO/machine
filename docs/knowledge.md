# 知识库与数据

## 缓存文件格式

`knowledge/cache/<material>/<name>.yaml`，两段式：frontmatter + 正文。

```yaml
---
data_source: GB/T 11362-2021《同步带传动 节距型号…额定功率和传动中心距计算》
second_source: 成大先《机械设计手册》第3卷 第14篇（纸质原件核对）
verification_status: single_source     # verified | single_source | self_defined
last_verified: 2026-09-17
verified_by: 张三
_todo: "需用 GB/T 11362-2021 表核对每种带型的 pb / vmax"
unit_notes:
  pitch_pb: mm
  vmax: m/s
---

# 正文注释会被完整保留（公式、用法、录入规则都在这里）
belt_types:
  H:
    name_zh: 梯形齿 H（重型）
    pitch_pb: 12.7
    vmax: 30.0
```

### 两段式的坑

PyYAML 的 `safe_load` 遇到多文档会抛 `ComposerError`。
必须用 `safe_load_all` 再把各文档合并到顶层 dict——`mds/knowledge.py` 就是这么做的。

这曾经是个真实 bug：原 `scripts/_yaml.py` 走 `safe_load`，
在装有 PyYAML 的环境下**读不了任何一张缓存表**。
之前能跑只是因为 PyYAML 缺失、回落到了 `yaml_mini`。

### 元数据字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `data_source` | ✓ | 主信源。标准号 + 表号，或手册名 + 卷/篇 |
| `second_source` | 标 verified 时必填 | 与主信源**相互独立**的另一份资料 |
| `verification_status` | ✓ | `verified` / `single_source` / `self_defined` |
| `last_verified` | ✓ | 最近一次核验日期 |
| `verified_by` | | 核验人，便于追溯 |
| `_todo` | | 待办。**必须是真键，不能写成注释** |
| `unit_notes` | | 单位说明，供人读 |

`_todo` 曾经全项目都写成 `# _todo:` 注释，程序读不到，
导致 `cache_manager report` 的 `todo_total` 恒为 0，待办追踪整个失效。
`scripts/migrate_todo_keys.py` 做过一次性迁移，**新表别再犯**。

## 双源核验

**标 🟢 必须填第二信源，且不能与主信源相同。**

这不是走形式。绿灯的意义在于"有两个独立信源相互印证且可追溯"；
填不出第二信源就说明还不该给绿灯。**假绿灯比没有绿灯更危险**——
它会让人以为这个数已经被验证过了。

对齐 `references/source_priority.md` 的规则：
关键工况系数需「≥ 第 2 级信源 + 至少 2 个独立信源」。

```bash
python -m mds verify synchronous_belt belt_pitch \
    --second-source "成大先《机械设计手册》第3卷 第14篇（纸质原件核对）" \
    --by "张三"
```

拒绝的情况：
- 第二信源为空 → `EditError`
- 第二信源与主信源相同 → `EditError`（"这不构成交叉验证"）
- 表里没有 `data_source` → `EditError`

**数据被修改后，已核验状态自动退回 `single_source`**，并写入待办
"数据在核验后被修改，需要重新双源核对"。改过的数不能继续顶着绿灯。

## 写入：保注释

`mds/editor.py` 用 `ruamel.yaml` 的 round-trip 模式。
PyYAML 落盘会把注释全部抹掉，而缓存文件的注释里是公式、用法和录入规则——
那些比数据本身还难重建。

写入前会存 `.yaml.bak` 备份。改错了能找回来。

可用接口：

| 函数 | 作用 |
|---|---|
| `set_sources()` | 改 `data_source` / `second_source` / `_todo` |
| `mark_verified()` | 标绿（守卫见上） |
| `unverify()` | 退回 single_source |
| `upsert_points()` | 往插值表某行补/改数据点 |
| `set_scalar()` | 改一个标量（如 `belt_types.H.vmax`） |

## 三层数据自检

```bash
python -m mds audit [material]        # 加 --no-probe 跳过探测，更快
```

### 第一层：frontmatter 体检

必填字段是否齐；标了 `verified` 的是否真有 `second_source`（假绿灯当场揪出来）。

### 第二层：静态覆盖分析

插值表的网格空洞。取所有行上出现过的 y 值并集，
报出每行缺哪些格子：`L 型 n1=2880 这一行缺 z1 = 18`。

### 第三层：动态可达性探测 ★

**按工作流的 `probe` 网格真跑一遍引擎**，报出哪些工况组合现在根本算不出来。

这一层最有用——它回答的是"这个软件现在到底能选什么"，
而不是"数据缺了几格"。用的是真引擎，不是模拟，所以不会与实际行为脱节。

### 缺口分类

| kind | 严重度 | 含义 |
|---|---|---|
| `fake_green` | 阻断 | 标了 verified 但没有第二信源 |
| `frontmatter` | 警告 | 元数据字段缺失 |
| `empty_group` | 阻断 | 某个分组整个没有数据 |
| `grid_hole` | 警告 | 插值表某行缺几个点 |
| `unreachable` | 阻断 | 某工况因数据缺失算不出来 |
| `no_solution` | 警告 | 该规格系列内无解（**不是数据问题**） |

数据类缺口带 `target`，含表名、分组、行坐标、缺哪些点——
界面据此直接跳到补录表单，预填好坐标。

### 为什么一张 🟢 都没有

第二阶段建的 19 张新表，多数都做了**两处独立电子转载互校**，
但两处转载是**同一份国标的两次转写**，不构成两个独立**信源**。

按 `references/source_priority.md` 的规则，绿灯的意义是"两个独立信源相互印证且可追溯"。
所以互校结果记在 `second_source` 字段里，状态仍留 `single_source`，
`_todo` 写明「标 🟢 需标准原件或纸质手册核对」——**那一步只有你能做。**

### 互校真的抓到了东西

这不是走形式。建表时逐格比对，抓到四处转写错误，一处都没录进去：

| 表 | 错误 | 怎么发现的 |
|---|---|---|
| `bolt/thread_series` | M30 的应力截面积被抄成 581（正确 560.6） | 定义式 `As = 0.7854(d−0.9382P)²` 一算就露馅，差 3.6% |
| `bolt/property_class` | 某处转载整体错行，4.8 级的 Rm 记成 500（应为 400） | 与另一处转载对不上，且违反等级代号的定义规则 |
| `shaft/material_stress` | 45 钢那一行的数值与 1Cr18Ni9Ti 行错位 | 45 钢的许用应力比 35 钢还低，不合常理 |
| `chain/chain_pitch` | 整张滚子链参数表列与表头错位（销轴直径当成内宽、链板高度当成极限拉伸载荷） | 08B 的"极限拉伸载荷 3.9 kN"明显不对 |

最后一例最能说明问题：**那张表除了节距一列，其余一律没录。**
节距之所以敢录，是因为它能由链号独立复算（前两位 ÷ 16 英寸 × 25.4）。

### 能复算的就复算

比"两处转载一致"更强的证据是**表值与定义式一致**。凡有定义式的，都写成了测试：

| 表 | 复算式 |
|---|---|
| `bolt/thread_series` | `As = 0.7854(d − 0.9382P)²`、`d2 = d − 0.6495P`、`d1 = d − 1.0825P` |
| `bolt/property_class` | 等级代号 x.y → `Rm = x×100`、`σs = Rm×y/10` |
| `chain/chain_pitch` | `p = 链号前两位 ÷ 16 in × 25.4`（05B 为公制例外） |
| `shaft/material_stress` | `A₀ = (9.55e6/(0.2[τT]))^(1/3)` 必须落在手册公布的 A₀ 区间内 |

### 拿不到数据时的三种处理

第二阶段反复遇到"这个数查不到可核对的出处"。处理方式一律不是编，而是换分工：

1. **改由用户填** —— 轴承的 C/X/Y、弹簧的 G、联轴器的工况系数。
   这些数印在厂商样本或材料证书上，抄它们比抄一张来路不明的表可靠。
2. **表里留空** —— 螺栓的合金钢安全系数、弹簧的 I/II 类应力比、
   齿轮的 ZH/YFa/σHlim。选到会如实报出缺口位置。
3. **整列不录** —— 链传动除节距外的全部参数。转载不可信就不录。

### 主要缺口

- **同步带**：`rated_power.yaml` 每种带型只有 1~2 个示例点，15 个工况里 9 个算不出来。
  完整数据需从 GB/T 11362 表 5~8 录入。
- **齿轮**：ZH、YFa、YSa、σHlim 都是**线图**，读不出数。
  因此只做几何计算 + 按用户给定系数的接触应力核算，**不做完整的 GB/T 3480 承载能力计算**。
- **链传动**：额定功率是曲线图，**选不了链号**——链号必须由用户指定。
- **弹簧**：I 类与 II 类的许用切应力比没有可核对出处（常被引作 0.3 / 0.4）。
- **螺栓**：合金钢 + 不控制预紧力这一档，信源只给笼统的「5.0~5.5」，未按直径分档。
- **密封件**：GB/T 3452.3 的沟槽尺寸与合格判据拿不到，压缩率只报数不判定。

### 一处已修正的元数据错误

`belt_pitch.yaml` 原本标注为 `GB/T 11362-2021《同步带传动 梯形齿带轮》`。
经核实这是**两份不同的标准**：

- **GB/T 11362-2021**《同步带传动 节距型号…梯形齿同步带**额定功率和传动中心距计算**》
- **GB/T 11361-2018**《同步带传动 节距型号…梯形齿**带轮**》

书名被安在了错误的编号上。标题已更正；
`pulley_teeth_min.yaml`（最小齿数属带轮参数）的归属存疑，已标待办待确认。

## 打包版的只读限制

安装版随包分发的数据是只读的（`config.knowledge_writable()` 返回 `False`），
所有写入接口返回 409 并说明原因。

要在打包版上改数据：设 `MDS_SKILL_ROOT` 指向一份可写的数据目录副本。
