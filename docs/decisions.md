# 决策记录

这里记的是**为什么这么做**，以及当时否掉了什么。

代码能说清"是什么"，说不清"为什么不是另一种"。想改设计之前先看这里——
下面每一条都有具体的代价在支撑，不是随手选的。

---

## 1. 工作流做成声明式 YAML + 解释器，不是每物料一个 Python 模块

**背景**：原 skill 的选型逻辑写在 `.md` 散文里，由 AI 读着执行算术。
`scripts/` 只有通用原语。也就是说当时是 **AI 在做确定的事**，
与产品理念"AI 做不确定的事，脚本做确定的事"正好相反。

**否掉的方案**：每个物料写一个 Python 模块（`synchronous_belt.py`）。
写起来最直接、调试最容易。

**为什么不**：trace 要手工拼；加物料必须改代码 + 重新打包；非程序员无法扩展。
而"新增物料 = 写一份 YAML"是这个产品的核心扩展性主张。

**代价**：需要一个受限表达式求值器和一套步骤类型抽象。
后来加润滑油时确实又扩了三种机制（见第 6 条），说明抽象不是一次到位的。

---

## 2. `NoSolution` 与 `DataMissing` 必须是两种东西

**发现于**：M3 的可达性审计。当时所有"所需带宽超出标准系列上限"
都被归成 `data_missing`，界面提示"请在知识库页补齐该数据表"。

**问题**：L 型带就是带不动 5.5 kW，数据一点问题没有。
正确的指引是**换带型**，不是补数据。两者给用户的方向完全相反。

**做法**：拆出 `NoSolution`，携带 `required` / `limit` / `remedy`。
界面、报告、审计三处分别措辞。

**验证**：拆完之后同步带的可达数从 3/15 升到 6/15——
因为那 3 个"失败"其实是引擎**正确地给出了答案**。

这条是整个项目里最有代表性的一次修正：*把两种不同的事情叫成一个名字，
会让软件说出误导用户的话。*

---

## 3. 分支用 `when:` 守卫，不用 `branch` 块

**背景**：M7 的润滑油是分支型工作流（链条 / 开式齿轮 / 导轨）。
计划里设想的是一个 `branch` 步骤类型，按枚举值切换后续步骤集合。

**改成**：每一步声明 `when:` 表达式，为假则标 `not_applicable` 跳过。

**为什么**：不需要嵌套结构（步骤列表保持扁平，静态校验也简单）；
表达力更强（任意条件，不限于枚举判等）；
天然产出 `not_applicable` 这个状态——而"本分支用不到"与"出错没跑到"
必须分开，混同会让人以为流程坏了。

**连带影响**：为了让分支守卫能比较枚举值，表达式求值器必须放开字符串常量。
放开范围严格限制在 `==` / `!=`，字符串参与算术会被当场拒绝
（`"a" * 10000000` 是内存炸弹）。

## 4. AI 自带账号（BYOK），软件不带 key

**否掉的方案**：软件内置 key 走中转服务，按用户订阅计费。

**为什么不**：
- 边际 AI 成本随规模线性增长（产品理念自陈的"劣势三"）
- 工况参数要经过我们的服务器——对"设计数据不外流"的工业客户是硬伤
- 需要维护一套计费与额度系统

**做法**：用户绑定自己的账号，请求本机直连。
（2026-09 起支持 DeepSeek / 火山方舟（豆包）/ 阿里百炼（千问）/ OpenAI，见第 18 条。）

**关键收益**（当初没预料到的）：这条约束逼出了
"**未绑定账号时软件必须完整可用**"，于是离线确定性内核从"降级方案"
变成了**默认形态**。这恰好就是产品理念三想要的架构。

**注意**：四家都没有面向第三方应用的 OAuth，所以不可能做成"跳转登录"。
只能是引导式的 API Key 绑定。别再去找 OAuth 方案了。

---

## 5. 只显示真实 token 与真实余额，不做费用换算

计划里写的是"显示预估费用"。

**否掉的理由**：单价会变。把价目表硬编码进来，早晚会给出一个过期的
"预估费用"数字。一个卖"不给来路不明的数字"的产品，
在自己的用量页上摆一个可能过期的估算，说不过去。

**改成**：显示本次调用的实际 token 数（含缓存命中），
以及 `/user/balance` 返回的真实余额。两样都是真的。

---

## 6. 决策表用 `table_pick`，不复用 `table_lookup`

**背景**：润滑油的表不是数值插值网格，而是决策表——
按速度档返回一整组推荐（VG 候选、基础油、添加剂、典型产品、注意事项）。

**否掉的方案**：用 `table_lookup` 取到那个 dict 再在结果模板里拆。

**为什么不**：`lookup` 的契约是"取标量"，取到 dict 会报错；
放宽它等于让一个步骤类型有两种返回形状，下游没法统一处理。

**做法**：新增 `table_pick`，显式声明 `fields:` 映射。
列表字段自动多产出 `<名>_first`——推荐往往是区间（VG 150/220/320），
但采购关键词只能带一个值。

---

## 7. 导出接口不接收前端传来的 trace

**否掉的方案**：前端把当前看到的 trace POST 给导出接口渲染。少一次计算。

**为什么不**：那等于让客户端决定报告内容。
报告是要拿去评审、归档、当采购依据的。

**做法**：导出接口只收输入参数，服务端自己重跑一遍引擎再渲染。
这保证了报告里那句"本报告可由这组输入完整复现"是真话。

**附带好处**：导出件永远反映当前数据，不会是某个旧快照。

---

## 8. PDF 用 reportlab 内置 CID 字体

**否掉的方案**：随包分发一个中文 TTF（思源黑体等）。

**为什么不**：字体文件几 MB 到几十 MB，且涉及授权。

**做法**：`UnicodeCIDFont('STSong-Light')` 是 reportlab 内置的，
不用外带文件、离线可用、无授权问题。

**代价**：CID 字体没有 emoji 字形。导出层统一剥掉 emoji——
文字本身已经把状态说清楚了。

---

## 9. 数据缺口不自动填补

审计能精确算出缺哪些格子。技术上完全可以用相邻点插值把空洞填上。

**为什么不**：那就是在伪造数据。

这个产品的全部价值在于每个数字可追溯。一个"系统推断出来的" P0 值
和一个抄自标准的 P0 值，在界面上长得一模一样——
这正是"拒绝外推"这条规则要防的事，在补数据这一侧同样成立。

**做法**：缺口清单精确到"哪张表、哪个分组、哪一行、缺哪几个点"，
点「去补录」跳到预填好的表单，人填。录入时**数据出处必填**。

---

## 10. 标绿必须有第二信源

**否掉的方案**：加一个"我确认过了"的勾选框。

**为什么不**：绿灯的意义是"有两个独立信源相互印证且**可追溯**"。
一个勾选框留不下任何可追溯的东西。

**做法**：`second_source` 必填，且不能与主信源相同，否则拒绝写入。
数据被修改后核验状态自动退回。

**副作用**：现在 11 张表全是 🟡。这是准确的现状，不是缺陷。
**假绿灯比没有绿灯更危险**——它会让人以为这个数已经被验证过了。

---

## 11. 打包版知识库只读

**为什么**：随包数据装在 Program Files 里本来就写不进去。
让用户点了编辑再失败，比提前禁用并说明原因糟糕得多。

**做法**：`config.knowledge_writable()` 在打包态恒返回 `False`，
写入接口返回 409 并说明"要补录请用源码方式运行，或设 `MDS_SKILL_ROOT`"。

**踩过的坑**：`ensure_engine_importable()` 会回写 `MDS_SKILL_ROOT` 环境变量，
一度让 `knowledge_writable()` 的 FROZEN 分支永远走不到。
现在用 `USER_SKILL_ROOT` 单独记住"用户显式设定的值"。

---

## 12. sidecar 回收做两道保险

**只做一道会留下孤儿进程。** 这是实测确认的，不是假想。

Tauri 的 `RunEvent::Exit` 只覆盖正常退出。任务管理器结束进程 / `taskkill /F` 时，
Rust 的 `Drop` 根本不会执行，`mds-server.exe` 会继续占着端口。

**做法**：第二道是 sidecar 自己盯 `--parent-pid`，父进程消失就退出。

## 13. `.md` 回填对齐 YAML，不让它退化成背景资料

**背景**：M1 把选型逻辑从 `.md` 散文搬进 YAML 之后，`.md` 就没人维护了。
到 M7 结束时，两份文档已经在好几处对不上——而 `.md` 是 skill 仍在读的那一份。

**否掉的方案**：让 `.md` 退化成纯背景资料，只留"选型目标""常见问题"这类不涉及数值的段落。
省事，也不会再对不上。

**为什么不**：对不上的那几处**恰好都是最危险的**——
`.md` 写着引擎根本不输出的压轴力 FQ，写着引擎没实现的油膜厚度校核，
写着一个量纲错误的导轨速度公式，还把 GB/T 11361 的书名安在了 11362 的编号上。
一份没人维护但看起来权威的文档，比没有文档糟。删掉这些段落等于承认软件功能变少了，
而实际上是**数据不够**——这个区别必须写出来。

**做法**（2026-09-22）：两份 `.md` 按 YAML 逐条回填。
每个计算步骤标出 YAML 的步骤 id，参数表抄真实 `domain`，
校核表只列引擎真在跑的那几项，算例是 `mds run` 真跑出来的结果。

新增一节 **「未实现项」**：凡是旧文档提过而引擎没做的，逐条写明**缺什么数据才能做**。
不是删掉，是说清楚。

两处转写勘误保留在文中而不是抹掉——`.md` 已按 YAML 更正，
同时写明「仍待标准原件确认」。**读者需要知道这个数被改过、以及为什么改。**

**连带改动**：`SKILL.md` 的路由改为先找 `.yaml`；`_template.md` 改成"先写 YAML 再回填 .md"，
并要求新物料必须写「未实现项」与「已验证算例」两节。

**代价**：以后改 YAML 要记得回填 `.md`。这条写进了开发自检清单。

## 14. 新增 `row_select`，而不是把同一份数据存两遍

**背景**：第二阶段反复出现同一个模式——*在有序行集里找第一个满足阈值的行，
取它整行的多个字段*。螺栓按 As 选规格、键按轴径查截面、O 圈按线径选档、
轴承按 C 选型号，都是这个动作。

**否掉的方案**：用现成的 `round_to_series`。它只能圆整**扁平数字列表**，
拿不回同一行的其它字段。绕开的办法是把同一份数据存两遍——
一份 `as_series: [5.03, 8.78, ...]` 给圆整用，一份 `by_as: {5.03: {d: 3, P: 0.5}}` 给反查用。

**为什么不**：**同一个数字存两处，迟早会对不上。** 这个项目的全部价值在于
每个数字可追溯，而两份副本一旦不一致，你无法判断哪份是对的。

**做法**：新增 `row_select` 步骤类型，语义是 `table_pick` 的阈值版。

**关键取舍**：**没有"取最接近的一行"这个退路。** `round_to_series` 有 `clamp` 模式，
`row_select` 刻意不给——给一个比所需规格更小的螺栓，比停下来说"系列内无解"危险得多。

选不中时还要分辨两种情况：阈值卡在系列上/下限 → `NoSolution`（该换设计）；
其它情况 → `DataMissing`（该补表）。这是第 2 条决定的延续。

## 15. 数据拿不到时改分工，而不是编数

**这是第二阶段最重要的一条。** 10 个新物料里，几乎每个都遇到"这个数查不到可核对的出处"。

**否掉的方案**：填一个"业内通行"的值。比如弹簧 I 类许用应力比 0.3、
切变模量 G = 79000 MPa、轴承载荷系数 fp = 1.2——这些数到处都能查到，写进去没人会质疑。

**为什么不**：到处都能查到**不等于**可追溯。一旦写进表里，它在界面上和抄自国标的数
长得一模一样，用户无从分辨。**这正是"拒绝外推"那条规则在数据录入侧的同一件事。**

**做法**：三种处理，按数据的性质选：

| 处理 | 适用 | 例子 |
|---|---|---|
| **改由用户填** | 这个数印在厂商样本或材料证书上 | 轴承的 C / X / Y、弹簧的 G、联轴器工况系数 |
| **表里留空** | 数确实该在表里，只是还没拿到 | 螺栓合金钢安全系数、弹簧 I/II 类应力比、齿轮 ZH |
| **整列不录** | 拿到的转载本身不可信 | 链传动除节距外的全部参数 |

第一种最容易被误解成偷懒。它不是：**轴承的 C 值印在样本上，
而不同厂商同型号的 C 确实有差异**——自建型号库反而会给出错的数。

**代价**：有些物料的表单变长了（轴承要填 4 个样本值）。这是诚实的代价。

## 16. 互校抓到四处转写错误，一处都没录

**做法**：每张新表尽量做两处独立电子转载互校，逐格比对，不一致的格子不录。

**结果**：抓到四处错误——
螺栓 M30 的应力截面积被抄成 581（正确 560.6）；
某处性能等级表整体错行（4.8 级的 Rm 记成 500）；
轴材料表 45 钢那一行与 1Cr18Ni9Ti 错位；
滚子链参数表整张列与表头错位（销轴直径当成内宽、链板高度当成极限拉伸载荷）。

**比互校更强的证据是复算。** 螺栓的 As、d2、d1，性能等级的 Rm 与 σs，
链条的节距，都有定义式。M30 那个错就是公式一算露的馅——差 3.6%，
两处转载对不上时，公式直接判了胜负。凡有定义式的都写成了测试。

**连带决定**：滚子链那张表**除节距一列外一律不录**。
节距敢录是因为能由链号独立复算（前两位 ÷ 16 英寸 × 25.4）。
整张表不可信时，挑着录比全不录更危险——你没法解释为什么这几列可信。

## 17. 齿轮与链传动只做能算的部分，边界写死在 notes 与测试里

**背景**：这两个是计划里就预告会留大缺口的。齿轮的 ZH、YFa、YSa、σHlim
在 GB/T 3480 里是**线图**；链传动的额定功率是曲线图。读不出可核对的数值。

**否掉的方案**：从线图上目测几个点插值，或者用文献里的拟合公式。

**为什么不**：目测的点和拟合的公式都会产出一个**看起来像标准值的数**，
而用户无从分辨。齿轮强度算错的后果是断齿。

**做法**：把边界划在"能算的"和"算不了的"之间，并且**写死三处**：

1. YAML 的 `notes` 里第一条就是「这不是完整的 GB/T 3480 承载能力计算」
2. `.md` 文档开头用引用块单独占一节说明
3. **测试断言**：`gear_basic.yaml` 的 `node_region_factor_ZH` 等必须保持为空字典，
   且校核项里不能出现"弯曲"二字

第三条是关键。前两条只是文字，后来人"顺手补全"时不会去读；
测试会红。空字典而不是缺键，是为了让"这些数拿不到"这件事**本身可见**。

**实际交付**：齿轮的几何计算（分度圆、齿顶圆、齿根圆、中心距、重合度、变位）
全部可用且精确——**这恰恰是工程中最容易算错的部分**。
链传动的几何与运动学同理，只是选不了链号。

## 18. 多服务商：能力探测，不是能力声明

**背景**：接入火山方舟（豆包）、阿里百炼（千问）、OpenAI。四家都号称
"兼容 OpenAI"，但兼容的程度不一样——方舟与百炼的官方文档都只演示了
chat.completions，没提模型列表接口；余额查询只有 DeepSeek 有。

**否掉的方案**：在服务商表里写一个 `supports_model_list: false`，代码照着办。

**为什么不**：**这四家的接口都在变。** 写死的断言迟早会过期，
而过期的断言比没有断言更糟——它会让软件拒绝一个明明已经可用的接口。

**做法**：`validate()` **真的去请求一次** `/models`，收到 404/405 才退回
最小对话探针。表里的 `may_list_models` 只决定"要不要先试一把"，不决定结论。

**连带的诚实义务**：退回对话探针意味着**要花用户的钱**。所以：

- 绑定对话框在**点按钮之前**就写明这家验证会消耗 token
- 绑定完成后如实报出具体消耗了多少（`ValidationResult.cost_hint`）
- 探针用 `max_tokens=1`，能多小就多小

几个 token 值不了几分钱。但"悄悄花掉用户的钱"和"如实说明"之间的差别，
不是钱的差别。

## 19. 同时绑定多家，一家生效

**否掉的方案**：沿用单绑定，换服务商就解绑再重绑。

**为什么不**：解绑会把 key 从系统凭据库**删掉**。一家余额用完想临时换一家，
代价是回控制台重新复制一遍 key——而且原来那家充值后还得再绑回来。

**做法**：`account.json` 升级成 `{active, bindings: {...}}`，每家一份凭据
（凭据库里各占一个 profile）。切换只改 `active`，**不动任何凭据**。

**必须处理的事**：老用户的 v1 文件要自动迁移并保持生效。
**不该因为软件升级而需要重新绑定**——有测试守着，也在真实数据上试算过。

---

## 20. 默认关掉"深度思考"

方舟与百炼的模型默认开启思维链。本软件的三个 AI 任务都要**结构化输出**
（意图解析、参数建议都是 JSON），思维链既不需要、又要多花钱、
还可能让模型在 JSON 前面吐一段推理文本导致解析失败。

两家的关法不一样——方舟是 `thinking: {type: disabled}`，
百炼是 `enable_thinking: false`，而且百炼的 qwen3 **非流式调用必须关**，
不关直接报错。差异登记在 `providers.py` 的 `extra_body` 里。

**边界**：`extra_body` 只能**补充**协议，不能改写。合并时用 `setdefault`，
`messages` / `model` / `stream` 这些核心字段改不掉——有测试专门试着改，
确认改不动。一个写错的 spec 不该能把用户的问题换成别的。

---

## 待定，尚无结论

这几个是已知的取舍点，还没到必须决定的时候：

**手机端离线计算**。现在手机走在线 API。真要离线得把引擎移植成 TypeScript，
那会导致同一份公式两处实现——与"可独立复现"冲突。
离线的真实痛点在不联网的 CAD 机（已被桌面版覆盖），暂不做。

**多方案对比**。SKILL.md 的边界情况要求"多解时列 2-3 个方案"。
现在 `select` 步骤只能选一个。要做成并列对比，trace 结构得支持多分支并存。

**离线参数建议**。同步带规格没有 `typical` 值，所以离线 `suggest` 给不出东西。
补 `typical` 需要手册依据——原动机类型和工作机类型直接决定 K_A，猜错一路错到底。
**不能为了让界面好看而编几个。**

**线图数字化**。齿轮的 ZH / YFa / σHlim、链传动的额定功率曲线、
轴承的 aISO 修正系数，都是线图。要么找到已数字化的版本，要么自己从图上取点——
后者会引入一个无法追溯的误差源，需要先想清楚怎么标注它的不确定度。

**"样本填入"要不要做成可保存的型号库**。轴承、联轴器、减速器现在每次都要重填
样本值。做成用户自己的型号库（而不是我们预置的）能省事，且不违反"不编数"——
数据是用户自己录的、带自己的出处。但要新增一层数据模型。

**互校到什么程度才算够**。现在的规则是"两处独立电子转载 + 能复算的复算"，
结果仍是 🟡。如果标准原件长期拿不到，是否该引入一个介于 🟡 和 🟢 之间的状态
（比如"多处转载一致且公式自洽"）？加状态会稀释 🟢 的含义，需要你定。
